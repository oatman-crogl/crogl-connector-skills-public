# Recorded Future

![status](https://img.shields.io/badge/status-draft-lightgrey) ![version](https://img.shields.io/badge/version-0.1.0-blue)

> **v0.1.0** — 2026-09-15 — Version and changelog tracking added retroactively; see below for this bundle's actual build/validation history.

One CLI: `scripts/recordedfuture.py`. Run `scripts/recordedfuture.py --help` for the subcommand list; `scripts/recordedfuture.py <subcommand> --help` for that subcommand's flags.

This skill is bound to one configured connector and resolves it automatically; you don't pass a connector name. The connector's base URL is the Recorded Future API root (`https://api.recordedfuture.com`); the server attaches the `X-RFToken` header.

## Scope boundary

This connector covers Recorded Future's **read-only, single-request lookup/search surface** -- every resource in it shares the same static `X-RFToken` credential and the same simple GET-or-POST-and-get-a-response call shape. It deliberately does **not** cover:

- **Cases** and **Analyst Notes** -- full CRUD/authoring workflows (create, delete, draft-preview-publish), not lookups.
- **Lists** -- custom entity-list CRUD (add/remove entities).
- **Alert *Update*** and **Playbook Alert *Update*** -- these mutate status/priority/assignee; only the read (search/detail) side of Alerts and Playbook Alerts is implemented here.
- **Detection Rules** and **Auto YARA/Sigma job creation** -- async job-submission-and-poll pattern.
- **Collective Insights** -- bidirectional submit-then-query workflow.
- **Fusion Files**, **Malware Intelligence query language**, **SOAR bulk enrichment**, **STIX/TAXII**, **Takedown API** -- each its own distinct call shape.
- **Sandbox**, **ASI (Attack Surface Intelligence)**, **PFI (Payment Fraud Intelligence)**, **RiskRecon** -- separate Recorded Future products on different hosts with different auth (Bearer tokens, a different API key scheme); they cannot share this connector's credential regardless of CLI design.

Any of these may become their own connector type later. Do not attempt to reach them through this connector -- none are wired into `RESOURCES`.

## Auth recap

The connector stores one field -- `api_key` -- and crogld attaches it server-side as the `X-RFToken` header on every call. This is a static, long-lived token generated by an Enterprise Administrator (not a per-user OAuth token). Every Recorded Future API surface used here also advertises an `oauth2` `authorizationCode`-with-PKCE scheme (`id.recordedfuture.com/authorize` / `/token`) in its OpenAPI spec -- **do not use or reference this.** It is the Swagger documentation site's own interactive login (it authenticates a human into the docs UI via `/.well-known/openid-configuration`), not an auth path available to a provisioned server credential; it requires a live browser redirect and has no client secret. Never ask the user for the API token during analysis, never print it, and never construct Recorded Future auth headers manually.

## Tool call shape

```bash
recordedfuture.py query --resource domain --param riskScore="[65,]" --limit 20
recordedfuture.py query --resource actor --param name=Sandworm --limit 10
recordedfuture.py get --resource ip --id 8.8.8.8
recordedfuture.py get --resource alert --id <alert_id>
recordedfuture.py riskrules --resource domain
recordedfuture.py metadata --resource playbook-alert-common
recordedfuture.py view-result --ref <ref> --row 1
recordedfuture.py grep --pattern riskRule
recordedfuture.py ls --path /
```

## Subcommands

| Subcommand | Purpose |
|---|---|
| `query` (`--resource`, `--param KEY=VALUE` repeatable, `--limit`, `--output`) | Search one resource. `--limit` defaults to 20, is code-enforced as `click.IntRange(1, 100)`, and maps onto that resource's own `limit` field (ignored for the two resources with no pagination concept -- see Resources table). Returns grouped PSV with a `ref` UUID for drill-down. |
| `get` (`--resource`, `--id`, `--extension`) | Hydrate one record by id. `--extension` is only valid for the seven entity types (Intelligence Card extension sub-query); every other resource ignores/rejects it. |
| `riskrules` (`--resource`) | List the risk-rule catalog for one entity type -- the live source of truth for `--param riskRule=...` values (see Query fields below; the full enum is intentionally not inlined in this file). Only company/domain/hash/ip/url/vulnerability have risk rules; malware does not. |
| `metadata` (`--resource`) | Fetch one of six small fixed reference lists: `actor-categories`, `malware-categories`, `playbook-alert-common` (valid statuses/priorities/categories), `links-events`, `links-entities`, `links-sections`. |
| `view-result` (`--ref`, `--row`, `--result-set`) | Drill into one row from a prior `query`. Pure cache read. |
| `upload-samples` | Upload sampled rows to the knowledge graph. Takes `--ref UUID` or `--from-file FILE`, the exact `--query` (JSON-encoded params) used to fetch them, and `--catalog-path`. |
| `refresh` | Walk every configured connector's catalog (resource -> field) and commit to the KG. Resources that require a filter to run at all (`identity-password-lookup`, `links`, `entity-match`) have no field tier -- they can't be sampled unfiltered. |
| `ls --path /<abs-path> --format json` | List this skill's Recorded Future connectors' schema by UNIX path. |
| `grep --pattern <text>` | String-search this connector's persisted KG catalog. |

## Context budget rules

- Default `--limit` is 20. Only raise it on explicit user request, and prefer narrowing `--param` filters first. `--limit` is code-enforced at a hard cap of 100 (independent of the Connect API's own higher vendor max of 1000) -- a request above that is rejected, not silently clamped.
- Render the fields per Rendering pattern below; don't paste full raw JSON for more than a couple of records inline.
- Drop raw JSON/PSV from reasoning after rendering the answer. Don't re-run an identical `query` already in context -- use `view-result` on the existing `ref` instead.

## Query fields

Every entity/search resource accepts `--param KEY=VALUE`, repeatable. Common fields across the seven entity types (`company`/`domain`/`hash`/`ip`/`url`/`malware`/`vulnerability`):

| Field | Example | Notes |
|---|---|---|
| `riskScore` | `--param riskScore="[65,]"` | Interval syntax: `[20,80]` inclusive both ends, `[20,)` open-ended above, `(,90]` open-ended below. Not applicable to `malware`. |
| `riskRule` | `--param riskRule=recentCncSite` | A single risk-rule id, **specific to each entity type** -- run `riskrules --resource <type>` first to get the live, current list rather than guessing a value. Not applicable to `malware`. |
| `firstSeen` / `lastSeen` | `--param lastSeen="-7d"` | Elasticsearch-compatible date format or relative term. |
| `list` | `--param list=<list-id>` | Filters to entities present on a specific custom list (List API id -- not resolvable through this connector). |
| `orderBy` / `direction` | `--param orderBy=riskscore --param direction=desc` | `orderBy` enum: `created`, `modified`, `sixtydayshits`, `sevendayhits`, `criticality`, `riskscore`, `totalhits`, `firstseen`, `lastseen`, `rules`. `direction` enum: `asc`, `desc`. |
| `fields` | `--param fields=risk,entity` | Comma-separated enrichment fields to include; see `metadata` endpoints and `docs.recordedfuture.com/reference/enrichment-field-attributes` for the full field catalog (not mirrored here -- too large and orthogonal to filtering). |
| `freetext` | `--param freetext=phishing` | Only on `company`, `url`, `malware`, `vulnerability` search -- not `domain`, `hash`, `ip`. |

Entity-type-specific fields not shared with the others:

| Resource | Field | Notes |
|---|---|---|
| `ip` | `range` | CIDR or `start-end` IP range. |
| `ip` | `location` | Recorded Future location ID (e.g. `I2EnW4` = Boston, MA). |
| `hash` | `algorithm` | One of `CRC-32`, `CTPH`, `MD5`, `SHA-1`, `SHA-256`, `SHA-512`. |
| `vulnerability` | `cvssScore` / `cvssV3Score` | Interval syntax, e.g. `[8.0,9.0]`. |
| `vulnerability` | `cpe` | CPE 2.3 identifier for the affected product. |
| `company` | `industry` / `domicile` / `parent` | Industry ID / country entity ID / parent-company entity ID. Resolve names to IDs via `query --resource entity-match`. |

`actor` search body fields: `name` (freetext match against actor name/aliases), `limit`, `offset` (pagination token, not an integer -- use the `next_offset` value from a prior response, not implemented as auto-pagination here).

`alert` search fields: `triggered` (interval), `assignee` (email, or `NONE` for unassigned), `statusInPortal` (`New`/`Resolved`/`Pending`/`Dismissed`/`Flag for Tuning`), `alertRule` (rule id), `freetext`, `orderby`=`triggered`, `direction`.

`playbook-alert` search body fields: `entity` (array), `statuses`/`priority`/`category`/`assignee`/`organisation` (arrays -- comma-separate the `--param` value, e.g. `--param category=domain_abuse,vulnerability`), `order_by` (`created`/`modified`), `direction`. Valid `statuses`/`priority`/`category` values come from `metadata --resource playbook-alert-common`.

## Uploading samples

`upload-samples` is provenance-anchored: every uploaded row must be the byte-identical output of a recent `query` issued from this same container. Capture the `Result reference: <uuid>` line `query` prints (or use `--output FILE` and pass `--from-file`), and pass the **exact same params** (as the JSON-encoded string `query` used for the read-before-write check) back as `--query`.

`--catalog-path` (required) is the inventory path the sample is recorded under -- typically `/<resource>/<field>` (e.g. `/domain/riskScore`).

## Rendering pattern

Render a compact card per record, not raw JSON/PSV:

- **Entity types** -- name/id, risk score, top contributing risk rules, first/last seen.
- **Actor** -- name, aliases, categories.
- **Alert** -- title/rule name, triggered time, status in portal, assignee.
- **Playbook alert** -- category, priority, status, created/updated.
- **Identity lookups** -- exposed identity/domain, dump/breach source, detection date. Never render a plaintext password back to the user even though the API may return one -- treat exposed credentials as sensitive regardless of source.

≤5 records → inline. More than that → show the first several plus a count of remaining matches, and offer to narrow the filter.

## Error handling

- **400** -- malformed filter syntax (e.g. a bad interval string on `riskScore`, or an invalid `riskRule` value for that entity type). Don't retry the same value; check `riskrules --resource <type>` for valid rule ids, or fix the interval syntax.
- **401** -- the stored `X-RFToken` is invalid or revoked. Surface this as a configuration issue for whoever set up the connector -- do not ask the user to paste a token into chat.
- **403** -- the token's account lacks the licensed module for this API surface (Recorded Future licenses modules separately -- e.g. Identity or Playbook Alerts may not be included in every subscription). This is a licensing/entitlement gap, not a bad credential; there is a dedicated `API Entitlements` reference endpoint (not wired into this connector) that diagnoses which modules are licensed, per Recorded Future's own docs -- surface the 403 as "this Recorded Future account may not be licensed for this module" rather than treating it like a bad token.
- **429** -- rate limited. Back off and report rather than retrying in a loop.
- **5xx** -- upstream Recorded Future service issue; report the status and retry only if the user asks.
- **Zero rows on a 200** -- a real, correct, empty result. Report it plainly and suggest loosening the filter rather than implying something is broken.

## Guardrails

- This connector is read-only. No write/update/create/delete action exists on any resource here -- do not imply alert triage, case creation, or list management is possible through it.
- Do not fabricate risk scores, risk rules, or identity-exposure data when a query returns zero results.
- Treat any identity/credential-exposure data (emails, passwords, hostnames) as sensitive -- summarize findings (e.g. "3 exposed credentials found for this domain, most recent 2024-06-01") rather than pasting raw exposed secrets into chat.
- Do not expose or reconstruct the API token.
- Do not attempt the OAuth2/PKCE `idp` scheme seen in every spec -- see Auth recap.

## Connector base URL

Configure the connector's base URL as `https://api.recordedfuture.com`. The CLI sends absolute, per-resource paths (`/v2/domain/search`, `/threat/actor/search`, `/alert/v3`, `/playbook-alert/search`, `/identity/credentials/search`, `/links/search`, `/entity-match/match`, ...) rather than relying on a path baked into the connector's base URL, since these resources live under different path prefixes on the same host.

## Required runtime env

`CROGL_MCP_URL`, `CROGL_CLI_TOKEN`. No upstream secrets -- the skill auto-resolves its bound connector; the server applies the `X-RFToken` header stored under that connector.

## Output format

`query` returns grouped PSV (header `#|`, data rows `<row_num>|`, `|` escaped as `\|`, cells over 1000 chars truncated). `get`, `riskrules`, `metadata`, and `view-result` return raw/pretty-printed JSON.
