# Proofpoint Email Security (ICES)

![status](https://img.shields.io/badge/status-draft-lightgrey) ![version](https://img.shields.io/badge/version-0.1.0-blue)

> **v0.1.0** -- 2026-07-29 -- Initial community connector bundle, built docs-only directly from the live Proofpoint-hosted OpenAPI spec at `developer.tessian.com/documentation/api` (fetched via a rendered browser session, not a search-result summary, since the page is a JS spec viewer). Read-only: list/query Security Events, User Groups, User Monitoring, Anomalies, Audit Trail; get one group by id; read a Custom Policy Configuration parameter. No credentials were available for this build -- nothing below has been exercised against a real tenant.

**STOP -- read this entire skill before running the CLI.** "Proofpoint Email Security" is ambiguous across at least three genuinely different products: this connector is scoped to the **ICES API** (`developer.tessian.com` — Proofpoint's rebrand of the acquired Tessian product, covering the Defender/Guardian/Architect modules). It is **not** the older Proofpoint TAP (Targeted Attack Protection) SIEM API (`tap-api-v2.proofpoint.com`, Service-Principal auth), **not** Proofpoint Essentials (SMB tier, `*.proofpointessentials.com`, Integration-Key auth), and **not** an on-premises Proofpoint Protection Server. These have different hosts, different auth, and different data models — a credential for one will not authenticate to another. If a user's tenant only has one of those other products, this connector is the wrong one for them.

One CLI: `scripts/proofpoint_ices.py`. Run `scripts/proofpoint_ices.py --help` for the subcommand list; `scripts/proofpoint_ices.py <subcommand> --help` for that subcommand's flags.

This skill is bound to one configured connector and resolves it automatically; you don't pass a connector name. This connector is **read-only** (GET only). The underlying API also exposes remediation actions (release/delete from quarantine, delete from inbox), group CRUD (create/update/delete/add-members/remove-members), and a Custom Policy Configuration *write* (set `keywords_list`) — none of those are wired into this CLI. Do not imply they're available through it.

## Subcommands

| Subcommand | Purpose |
|---|---|
| `query` (`--resource`, `--filter`, `--limit`, `--output`) | List a resource (`events`, `groups`, `users`, `anomalies`, `audits`). Checkpoint-paginates up to `--limit`. Returns grouped PSV + a result `ref`. |
| `get` (`--resource groups` only, `--id` required, `--limit`) | Hydrate one group by id, including its member list. The only resource in this API with a get-by-id endpoint. |
| `get-policy-parameter` (`--parameter-id`, defaults to `keywords_list`) | Read a Custom Policy Configuration parameter's current value (read-only — no write wired in). |
| `view-result` | Re-print one cached row from a prior `query`. |
| `refresh`, `ls`, `grep`, `upload-samples` | Standard KG catalog/sample commands. |

## Auth recap

The connector stores two fields — `host` (the customer's full Proofpoint Portal host, e.g. `yourcompany.tessian-app.com`, bound into `base_url` as `https://<host>`) and `api_token` (secret). crogld injects the token server-side as `Authorization: API-Token <token>` — **not** `Bearer`. The agent must never construct this header, ask the user for the token, or print it.

The token is generated by a Portal user whose role has both **Integrations** and **Security Events** permissions, from **Integrations -> Security Integrations -> Proofpoint API** (per the vendor docs — this exact menu path was not independently screenshot-confirmed against a live console; see the provisioning guide). The token always carries the same permissions as the user who created it, and is shown only once at creation. Per-endpoint permission gating (from the vendor docs):

| Endpoint(s) | Portal permission required |
|---|---|
| Security Events, get-policy-parameter, everything not listed below | Security Events |
| User Groups | Groups |
| User Monitoring | User Monitoring |
| Audit Trail | Audit Trail |

If a query 403s, the token's owning user's role is likely missing the specific permission for that resource, not a bad token.

## Host / region setup

The API host is region-specific: **EU** tenants are on `*.tessian-platform.com`, **US** tenants on `*.tessian-app.com`. The subdomain is the customer's own Portal subdomain — the same one they see in their browser URL bar when logged into the Proofpoint Portal. There is no separate discovery call for this; the customer must supply the exact host they see in their own Portal URL.

## Tool call shape

```bash
proofpoint_ices.py query --resource events --filter "created_after=2026-07-28T00:00:00Z" --limit 25
proofpoint_ices.py query --resource groups --limit 25
proofpoint_ices.py query --resource anomalies --limit 25
proofpoint_ices.py get --resource groups --id 42
proofpoint_ices.py get-policy-parameter --parameter-id keywords_list
proofpoint_ices.py view-result --ref <ref> --row 1
proofpoint_ices.py grep --pattern intent_types
proofpoint_ices.py ls --path /
```

`--resource` on `query` defaults to `events`; pass `--resource groups`/`users`/`anomalies`/`audits` explicitly for the others.

## Query model

`--filter` is a raw `k=v&k2=v2` string appended as query params — this API is **not** a query language (no KQL/SPL/SQL). Only one resource documents a filter param at all:

- **`events`**: `created_after` (ISO 8601 timestamp) — only include events created after this time.
- **`groups`, `users`, `anomalies`, `audits`**: no documented filter params besides pagination — an empty `--filter` returns all rows up to `--limit`.

Pagination is a **checkpoint cursor**, not offset/page-number: the CLI follows it internally up to `--limit` (`after_checkpoint` query param, driven by a `checkpoint` value in the response). The response envelope's array key and "more results" flag key are **not uniform across resources** — `events`/`users`/`audits` use `results`/`additional_results`, `groups` uses `groups`/`additional_results`, and `anomalies` uses `data`/`has_more`. This is handled internally; it only matters if you're reading a raw response directly.

**Anomalies checkpoint quirk (vendor-documented, not live-confirmed):** the `anomalies` endpoint's checkpoint is scoped to *the day it was issued*, not a rolling cursor — reusing an old checkpoint will never return anomalies identified after that day, even on repeated calls. If you need the latest anomalies, call with no `--filter`/checkpoint rather than reusing an old `ref`'s checkpoint state.

## Context budget rules

- Default `--limit` is 5 rows; hard cap is 25 — the CLI enforces this even on an explicit "all"/"everything" request. (The vendor API itself allows far more per page — up to 100 for events, up to 2000 for users — but this connector caps tighter to protect context.)
- Render the fields relevant to the user's question; don't paste full raw JSON for more than a couple of entities. Reuse an existing `ref` via `view-result` instead of re-running an identical query.

## Resources

- **`events`** (`/api/v1/events`) — Security Events from the Defender (inbound phishing), Guardian (misdirected/misattached outbound email), and Architect (outbound policy) modules. Discriminated by a `type` field (`defender`/`guardian`/`architect`); each carries module-specific detail (e.g. Defender's `intent_types`, `threat_signal_types`; Guardian's `triggered_filter_names`, `breach_prevented`; Architect's `triggered_policy_names`).
- **`groups`** (`/api/v1/groups`, `/api/v1/groups/{id}`) — named collections of email addresses/domains. `query --resource groups` returns flat metadata (`name`, `id`); `get --resource groups --id <id>` hydrates one group's members (its own separately-paginated `members` array).
- **`users`** (`/api/v1/monitoring/users`) — per-user deployment/onboarding status (`SyncState`: `LIVE`/`ONBOARDING`/`QUEUED`/`OUT_OF_DATE`; `UserMonitoringStatus`: connection health).
- **`anomalies`** (`/reporting/anomalies/v1`) — email-exfiltration anomaly detections: address, severity (`moderate`/`high`/`very_high`), anomalous period start/end, attachment count. See the checkpoint quirk above before assuming this pages like the others.
- **`audits`** (`/api/v1/audits`) — usage/config-change log: timestamp, type, category, human-readable details, acting user, source IP.

## Uploading samples

`upload-samples` is provenance-anchored: every uploaded entity must be the byte-identical output of a recent `query` from this same container. Use `--ref UUID` or `--from-file FILE` (a `query --output` artifact). Pass the exact `--filter` value used for the originating query as `--query` (empty string if none). `--catalog-path` is `/<resource>/<field>` (e.g. `/events/intent_types`).

## Rendering pattern

Render a compact table, not raw JSON, for more than a couple of rows:

- **Events**: type · created_at · (defender: intent_types; guardian/architect: triggered_filter_names/triggered_policy_names) · portal_link.
- **Groups**: id · name · created_at.
- **Users**: address (or equivalent identity field) · sync_state · monitoring_status.
- **Anomalies**: address · severity_label · anomalous_period_start · anomalous_period_end.
- **Audits**: timestamp · type · category · user · details.

≤5 rows → inline table. More → show the first several plus a count of remaining matches, and offer to narrow with `created_after` (events) or raise `--limit`.

## Error handling

- **400** — a bad query parameter or value (e.g. malformed `created_after`). Fix and retry once rather than trial-and-erroring.
- **401** — the API token is invalid, expired, or was deleted from the Portal. Surface as a connector-config issue; never ask the user to paste a token into chat.
- **403** — "Invalid token or API is not enabled" per the vendor's own error text — this can mean either a bad token *or* the token's owning user's role lacks the specific permission for that endpoint (see the permission table in Auth Recap). Check which resource 403'd before assuming it's a blanket auth failure.
- **404** — on `get`/`get-policy-parameter`, the id/parameter isn't recognized (reported as not found).
- **413** — response too large for a write endpoint (not reachable from this read-only CLI, but documented on the vendor's parameter-update endpoint — noted here in case a future write surface is added).
- **429** — rate-limited; the vendor docs state exact limits are "subject to change" and don't commit to a fixed number — back off and report rather than retrying in a loop. This has not been exercised live.
- **5xx** — upstream Proofpoint/Tessian service issue; report the status and retry only if the user asks.
- **Empty result on a 200** — a real, correct empty result (e.g. no anomalies detected, no events in the window), not an error. Report zero plainly rather than retrying.

## Guardrails

- **Read-only.** No write/remediation actions exist here — do not imply quarantine release/delete, inbox delete, group create/update/delete/add-members/remove-members, or policy-parameter updates are possible through this connector, even though those endpoints exist in the vendor API.
- Do not conflate this with **Proofpoint TAP**, **Proofpoint Essentials**, or an **on-premises PPS** deployment — different products, different auth, different hosts (see the top of this skill).
- Never reveal the `api_token` value.
- Don't fabricate data when a query returns zero results — report zero plainly and suggest widening `created_after` or checking whether the underlying condition (a policy, a device enrollment) exists yet.
- Nothing in this bundle has been live-tested against a real Proofpoint tenant. If a live query behaves differently from what's documented here (a different envelope key, a different permission error), treat the live behavior as authoritative and flag the discrepancy back rather than insisting on this doc.

## Connector base URL

Configure the connector's `host` field as the customer's **full** Proofpoint Portal host (e.g. `yourcompany.tessian-app.com` for US, `yourcompany.tessian-platform.com` for EU) — Crogl binds this into `https://{host}`. The CLI sends absolute API paths (`/api/v1/events`, `/api/v1/groups`, `/reporting/anomalies/v1`, `/filters/parameters/v1/{parameter_id}`).

## Required runtime env

`CROGL_MCP_URL`, `CROGL_CLI_TOKEN`. No upstream secrets are present in the agent container — the skill auto-resolves its bound connector; the server applies the `Authorization: API-Token` header stored under that connector.

## Output format

`query` returns grouped PSV (header `#|`, data rows `<row_num>|`, `|` escaped as `\|`, cells over 1000 chars truncated). `get`, `get-policy-parameter`, and `view-result` return full JSON.
